# 代码格式规范

本文件规定 VxAPO 各仓库的**代码格式**。核心只有一条：**格式不由人决定。**

它对应 `vxapo-format-policy-plan.md` 的执行结果，并把结论固化在这里——
原始计划文件随时可能被删除，本文件才是长期依据。

---

## 1. 单一权威

格式**只由 `cargo fmt` 决定**。

| 项目 | 值 |
|---|---|
| 折行策略 | **rustfmt 默认值**（无任何自定义 width 参数） |
| `style_edition` | `2021`（显式钉死） |
| `newline_style` | `Unix` |
| 工具链 | `channel = "1.97.1"`（`rust-toolchain.toml` 钉死） |

`style_edition` 显式钉死，是为了让将来 crate 的 `edition` 从 2021 升到 2024 时
**不会**被迫再做一次全仓重排。`newline_style = "Unix"` 与 `.gitattributes` 的
`eol=lf` 对齐。

配置文件位置：

| 仓库 | `rustfmt.toml` / `rust-toolchain.toml` |
|---|---|
| `vxapo-driver` | 仓库根 |
| `vxapo-cli` | 仓库根（成员 `protocol/` 共用） |
| `vxapo-app` | **`src-tauri/`**（仓库根不是 Cargo 包） |

三份配置**逐字节相同**，可用哈希校验：

```sh
sha256sum vxapo-driver/rustfmt.toml vxapo-cli/rustfmt.toml vxapo-app/src-tauri/rustfmt.toml
```

### 为什么选默认值而不是 `use_small_heuristics = "Max"`

两种方案在 driver 全仓的实测对比：

| 方案 | hunk | 新增 | 删除 | 净变化 | >90 列行数 |
|---|---|---|---|---|---|
| **默认（采用）** | 445 | 1802 | 991 | +811 | **257** |
| `Max` | 504 | 962 | 1885 | −923 | **431** |

`Max` 会把 `>90` 列的难读长行从 287 增加到 431（+68%），且需要长期维护一份自定义配置。
默认值则无需任何本机配置——任何编辑器 / CI / 后续工具开箱即产出同一格式。

## 2. `cargo fmt` 的等价机械改动

审查格式化提交时，以下几类改动**不是**逻辑改动：

1. **删除文件开头的 UTF-8 BOM**（U+FEFF）——driver 曾有 17 个文件带 BOM。
2. **补齐多行构造的尾随逗号**。
3. **重排 `use` 列表与 `mod` 声明**（按字典序）。
4. **给单表达式分支加/去花括号**（`=> expr` ↔ `=> { expr }`）。
5. **给尾表达式补分号**（`else { return }` → `else { return; }`）。

已验证：driver 格式化提交的 95 个文件，在「空白 + BOM + 逗号 + 花括号 + 分号 +
`use`/`mod` 重排」全部归一后，字符流完全一致——**零逻辑改动**。

## 3. 提交纪律

### 3.1 fmt 提交必须纯净

**逻辑改动不得与整仓格式化放进同一提交。**

原因：`.git-blame-ignore-revs` 依赖「该提交是纯格式化」这一事实才能安全跳过它。
一旦夹带逻辑改动，blame 会连真实改动一起忽略，等于毁掉可追溯性。

### 3.2 blame 保护

每个仓库都有 `.git-blame-ignore-revs`，登记纯格式化提交的完整 hash。
每台机器需执行一次（GitHub 网页端会自动识别该文件）：

```sh
git config blame.ignoreRevsFile .git-blame-ignore-revs
```

> **实测说明（driver，2026-10）**：格式化提交之后，全仓仅 27 行仍归属该提交，
> 且全部是 rustfmt **新造**的结构行（`}`, `},`, `);`, `assert!(` 等）——
> 这类行没有「前身」，本就不受 ignore 影响。而**纯缩进移动**，git 自己就能正确
> re-attribute，不需要 ignore 文件介入。因此该文件在本轮**无可测收益**，
> 但对将来「升级 rustc 导致输出变化」那种真会移动大量既有行的重排依然有效，故保留。

## 4. 门禁

### 4.1 本地 pre-commit hook

各仓 `.githooks/pre-commit` 在提交前跑格式检查，未通过则拒绝提交。
hook **只检查、不改写**——自动 fmt 会把未预期的改动混进提交、掩盖真实内容。

**hook 不随 clone 传播**，新克隆的机器必须执行一次：

```sh
git config core.hooksPath .githooks
```

### 4.2 编辑器

`.vscode/settings.json` 已入库（`editor.formatOnSave` + rust-analyzer），
保存 Rust 文件即自动格式化。

### 4.3 CI（未实施）

四仓均有 GitHub 远端，可在 `.github/workflows/` 加 `cargo fmt --all -- --check`
与 clippy。**本轮未创建**，属可选加强。

## 5. 各仓差异（**执行时最容易错的地方**）

| 仓库 | 格式检查命令 | 说明 |
|---|---|---|
| `vxapo-driver` | `cargo fmt --all -- --check` | 自包含 |
| `vxapo-cli` | `cargo fmt -p vxapo-cli -p vxapo-protocol -- --check` | **不可用 `--all`**，见下 |
| `vxapo-app` | `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` | 根不是 Cargo 包 |

### `vxapo-cli` 的越界陷阱

`vxapo-cli` 通过 path 依赖 `../vxapo-driver`，因此 **`cargo fmt --all` 会连带
格式化 driver 的文件**。实测：

| 命令 | 总 hunk | 其中 driver 的文件 |
|---|---|---|
| `cargo fmt --all` | 589 | **445** |
| `cargo fmt -p vxapo-cli -p vxapo-protocol` | 141 | 0 |

后果：driver 的文件会出现在 cli 仓的提交里，破坏仓库边界，让 blame-ignore 与回滚复杂化。
**故 cli 仓一律用显式 `-p`。** driver 的文件只在 driver 仓库里改。

## 6. 行尾

- `.gitattributes`：`* text=auto eol=lf`，`*.cmd` / `*.bat` 例外保持 CRLF。
  四个仓库该文件的有效规则完全一致。
- 这层按 git 规则**覆盖全局 `core.autocrlf`**，因此不会再有
  「内容没变却显示已修改」的假改动。
- `.editorconfig` 管非 Rust 文件（缩进、行尾、末尾换行）。

> **注意**：`vxapo-app/.gitignore` 是 **GBK 编码**（不是 UTF-8），
> 改动时必须按字节处理，不要当成 UTF-8 重写。

## 7. 升级 rustc 的流程（**独立事件**）

rustfmt 输出随版本漂移。**不要**把升级和格式化混在一起：

1. 先单独完成 rustc / 依赖升级并提交（格式可能暂时为红）。
2. 升级后逐仓单独跑格式命令，**若输出有变化**：
   - 单独成一个 `style:` 提交（遵守 §3.1 的纯净要求）；
   - 把该提交完整 hash 追加到该仓 `.git-blame-ignore-revs`；
   - 同步更新该仓 `rust-toolchain.toml` 的 `channel`。
3. 若输出无变化：只更新 `rust-toolchain.toml` 即可。

三个 Rust 仓库钉同一版本，升级时 `rust-toolchain.toml` 要**一起改**。

## 9. 定点豁免

个别宏展开 / 手工对齐表确实被折得难读时，用 `#[rustfmt::skip]` **定点**豁免，
并写明理由。**大面积使用属反模式**——它会重新制造不一致。

本计划执行过程中**未使用任何** `#[rustfmt::skip]`。

> 唯一一处例外处理：`src/object/apo/rtdump.rs` 把单行
> `if x { unsafe { .. } } else { .. }` 交给 rustfmt 展开后，原本写在 `let` 上方的
> `SAFETY` 注释与 `unsafe` 块之间多出一行 `if`，触发
> `clippy::undocumented_unsafe_blocks`（driver 在 `lib.rs` 中 deny）。
> 修法是把 SAFETY 注释移到 `unsafe` 块正上方，**未使用** `#[rustfmt::skip]`。
> 该修复单独成提交，不并入格式化提交。
