## Design principles

1. Light/dark share the same structure; only CSS variables change. Color variables are registered with `@property` and interpolated during a 0.35 s theme transition.
2. All positioning and animation snap to device pixels via `snapPx()`.
3. Interaction stability comes before motion; animations must not change interaction results and can be interrupted.
4. Hover, drag, and marquee are pointer-level interactions; desktop-first, mouse/trackpad friendly.
5. Scrollbars are custom-drawn: they take no layout width, appear only on genuine user scrolling, auto-fade after 1.2 s idle, and are not re-triggered by programmatic scrolling (view switch / height collapse).

## 01 Design foundations

- Theme tokens: background, surface, text, accent, border, shadow, hover states for light and dark, plus curve/scrollbar/slider tokens (`--curve-path`, `--curve-axis`, `--scrollbar`, `--thumb`, `--gs-thumb-*`).
- Dark axis color is `#7c7d7f`; dark scrollbar is `#3f4348` / hover `#4f5358`.
- Z-index hierarchy: content 1, bottom row/toolbar 20, selection toolbar 30, marquee 40, scrollbar (non-dialog) 50, dialog overlay 60, dialog content 61, scrollbar (in dialogs) 65, Toast 70, drag flight copy 70 and drag capture overlay 75 (both portaled into the scroll container, hence inside `.device-body`'s stacking context and clipped at the content edges — the tab bar's 40 covers them by design).

## 02 Shell and navigation

- Window skeleton with custom title bar (window controls); TopBar: logo, settings/import/export, semantic/parameter view switch, window controls. The view switch is wrapped in a `.view-seg-zone` "dead zone" (`padding: 8px`, carries no `data-tauri-drag-region`): a mis-aimed click next to the control lands there instead of the title-bar drag region, so it cannot trigger the title bar's double-click maximize/restore.
- View switch `.view-seg`: centered segment with sliding thumb (`--brand-bg` + `--brand` border), 0.25 s slide; disabled rules per view.
- Sidebar: segmented switcher (Preset | Custom | Advanced); preset/custom entries are compact pills with an 8 px accent dot, bold group name, and 12 px weak subtitle (`flex + gap` layout); advanced section uses category + pill rows.
- Device tabs: `tab-btn` (13 px, 16 px radius), tuning dot switch (`.tab-dot`), close button, add button; per-device tuning state initialized from disk.
- Empty state: centered logo + install row when no devices; the plus and install button use 0.18 s hover transitions, and the tip color follows theme variables (no lag on theme switches).

## 03 Views and cards

- Semantic view (`PresetView`) and parameter view (`AdvancedView`) share `.view-stage`; switch animation is a 0.32 s x-slide (the entry does not tween opacity — the cards handle the fade-in, see 06). Both views stay in the DOM (no `AnimatePresence` mount/unmount): the outgoing view gets `.is-exiting` (absolute positioning) for the slide, then is hidden with `display:none` — this avoids rebuilding the 31 parameter-card subtrees. A height collapse with scroll restoration follows. Enabling the channel selector no longer disables the semantic view or forces the parameter view: the semantic view filters by channel too (`PresetView`'s `visible`), and the channel entry point is the curve card's selector, present in both views.
- Card grid: 2–5 columns by width (900/1200/1700 px breakpoints), 12 px gap; group cards span all columns.
- Group cards (`.group-card` / `.sem-group`): accent edge, enable dot, group name (editable via `.sem-select`), chips; filter cards (`.band-card`): enable dot, type, params (slider + gain input); effect cards (`.effect-card`): dot, name, description, param rows, semantic strength row.
- Built-in effects: preamp, wide (Stereo Field), aural, reverb (Plate), compressor, loudness (Loudness EQ); semantic strength maps to core params (see App Reference Specification §6).

## 04 Curve and device panel

- Frequency response curve with `CurveGrid` (dashed Y/X grid lines; axis in `--curve-axis`), `CurvePlot` (path in `--curve-path`); coordinates via `lib/curve.ts` (`logX` / `dbY`). The Y range from `axisRange(peakGain, troughGain)` is **aligned to a multiple of the grid step** (2 dB, or 4 dB past a 26 dB span: rounded to 2 dB first, soft-clamped to 6–30, then aligned, converging in at most two passes), so the grid runs exactly from `yTop` to `yBottom` — the first and last lines sit on the plot edges and 0 dB always lands on a tick. Row positions are then `snapPx()`-rounded (spacing is often fractional, e.g. `180×4/32 = 22.5px`; subpixel text gets rounded by the renderer, which is the "tick numbers randomly drift downwards" bug) and labels use `dominantBaseline="middle"` rather than a hand-tuned `+3` offset. (The grid used to floor/ceil to step multiples on its own, while the range was computed elsewhere — when the range was not a step multiple the first line fell half a cell short of the top edge.)
- Evaluation points: 20 Hz–20 kHz log sweep (481 points) + band centers + high-Q refinement + neighbor midpoints. The curve card's channel selector lists the channels when channel mode is on (switching drives `setActiveChannel`, the global active channel); with it off it shows "all channels". The card exists in both views, so channel switching works from the semantic view as well. Its width is measured once in a `useLayoutEffect` before first paint (the state's initial value is only a window-width fallback) — otherwise the SVG's viewBox would be laid out from the estimate and then jump when the `ResizeObserver` corrected it.
- Performance: `useThrottledCompute` recomputes at 42 ms (≈24 fps) while dragging; RBJ coefficients cached.
- Device properties card (GUID/version/mode/slots/EAPO), normalization button; glassmorphism on both bottom cards.
- Curve hover tip: exponential follow (8% per frame), 280 ms side-flip, horizontal/vertical avoidance.

## 05 Dialogs and selection

- Radix Dialog based overlays (`vx-dialog-overlay` z-60 / content z-61); settings (theme three-state + language), install (with `--verify` progress loop and `InstallResult`), uninstall, save preset (name + color swatches + per-band descriptions, empty by default; no intro field), import (TOML preview), confirm.
- Selection toolbar with save/delete/copy-to-channel actions; copy button uses a low-contrast background.
- Custom overlay scrollbar (`OverlayScrollbar`): no layout width; appears on wheel/touch/thumb drag only; fades out after 1.2 s idle (0.25 s opacity); survives device switches; z-index 50 normally, 65 inside dialogs.
- Toast: fixed bottom-center, `--accent-bg`, 0.2 s entrance.

## 06 Drag and motion

- Custom pointer-level drag engine (`useDragSort`): 500 ms enter debounce (must exceed `LAYOUT_ANIM_MS` + `ANIM_SETTLE_BUFFER_MS` = 480 ms), 400/320 ms layout animations on `LAYOUT_EASE`, 80 ms settle buffer booked against the duration actually used (an outside-slot move waits 320 ms, not 400 ms), 48 px outside distance, and a 530 ms fly landing (`FLY_ANIM_MS` 400 + `FLY_HOLD_MS` 100 + `FLY_TAIL_MS` 30; the position segment is `FLY_MOVE_RATIO` 0.72 = 288 ms, and the framer `x`/`y` `times` and the shadow-tail `times` are derived from that same ratio). Pointer moves and scroll events are coalesced into one `requestAnimationFrame` settlement per frame (shift slots, then position + hit-test), because high-rate pointers deliver hundreds of events per second and handling each one would rewrite styles and re-measure rects inside a single frame; the release flushes any pending frame first, so the flight starts where the pointer actually stopped. The grabbed overlay follows the pointer with `transform: translate()` (`left`/`top` stay 0 as the static basis — writing `left`/`top` every frame is a layout write — and no `translate3d`/`will-change` is used on purpose, so the card is not promoted to a composited layer that would change text rasterisation while the pointer rests). Slots shift with the page scroll during a drag (the hit test re-runs from the last pointer position), the landing point is re-measured after the synchronous reorder, and the flight animates `x`/`y` (composited, snapPx-aligned) with a static size. The flight's basis is the landing point itself, with path offsets measured from it and a final frame of 0, so a cached transform rewrite cannot shift the landing; shortly after the motion ends the flight drops `transform`/`will-change` and returns to normal painting (a layer that stays composited renders text at a different raster/antialiasing quality). The release settles on the already-confirmed slot instead of re-testing the pointer (so the placeholder never jumps at release and the landing matches what the user saw), and `finalizeDrop` is deferred out of the `pointerup` handler so the input pipeline is not blocked. The flight copy is portaled into the scroll container (`.tuning-scroll`) and positioned in content coordinates (viewport position minus the container rect plus `scrollTop`, converted once when the flight starts), so it scrolls with the content: the browser follows it on the compositor thread, with no JS compensation and no lag. (Two historical detours: it was first a fixed top-level layer with a per-scroll-event JS compensation, which lagged a frame and jittered visibly; that compensation also had its sign inverted at first — the landing basis is in viewport coordinates, so it has to be shifted *with* the content, `+dy`.) The grabbed overlay is portaled into `.device-body` (deliberately *not* the scroll container) and keeps `position: fixed`: it stays in viewport coordinates and never moves with the scroll — that is what locks it to the cursor. It is clipped at the content edges by `.device-body`'s `clip-path: inset(0)` (clip-path clips the whole subtree, fixed descendants included) and its top-left corner is clamped inside the content-area rect (`.content`) with an inset of `DRAG_BOUNDS_INSET_PX` = 8 (it must not hug the edge): `[bounds.left + 8, bounds.right − cardW − 8] × [bounds.top + 8, bounds.bottom − cardH − 8]` (measured once at grab time). A web page cannot confine the system cursor, so what gets confined is the card — the pointer keeps moving, the card stops at the edge. Hit-testing uses the **card centre** (`DragSession.curMidX/curMidY`), not the pointer: once the card is clamped the pointer may already be outside the content area, and testing against it would read as "outside every slot" and throw the placeholder to the end (this was a real bug — the placeholder no longer follows what you see). "Outside every slot = append to the end" still works: drag the card into the blank area below the cards (more than 48 px from every slot). The flight start rect is still read from the overlay's actual box. When the clamped card sits on the top/bottom edge and the container can still scroll that way, the drag drives the page: `EDGE_SCROLL_SPEED_PX_S` = 600 px/s converted per frame (frame-time based, so 60/120 Hz feel alike, long frames capped at 64 ms), continuing while the pointer is still, and stopping when the edge is left or that end of the scroll range is reached. Counter-example that was tried and reverted: giving a container a `transform` so the `fixed` overlay uses it as containing block — inside a scroll container that containing block travels with the content, and the card ends up offset by exactly the scroll amount. Both layers therefore live inside `.device-body`'s stacking context, which sits below the tab bar's 40 — the tab bar and the content-area edge cut off both of them. The avoid curve `LAYOUT_EASE` and the view-collapse curve `COLLAPSE_EASE` are the same constant (`EASE_OUT_SOFT = cubic-bezier(0.22,1,0.36,1)` in `lib/motionEase.ts`, also used by the scrollbar-thumb morph), and `lib/dragSortTypes.test.ts` pins the timing relations (debounce lower bound, the three fly segments, the position ratio, the shared curve, and the CSS landing-bar duration vs the flight).
- Marquee selection (`useMarqueeSelection`): dashed box, hit-testing limited to the current view stage during view switches.
- Animation table: view switch 0.32 s + 800 ms collapse (entry does not tween opacity; the cards handle the fade-in), device page 180 ms fade-out (`DEVICE_FADE_MS`; the entry does not tween opacity either, `AnimatePresence mode="wait"` with `key=<device>` — the exiting element keeps the previous device's props, which is why page data flows down as props rather than store subscriptions), selection-toolbar glass 180 ms via `--glass-t` (the exit waits the same 180 ms before unmount so the tint canvas can fade), tab 0.15 s, card hover 0.18 s, dialog 0.18 s, toast 0.2 s, drag 320–530 ms (landing bar 0.4 s, matching the flight), curve tip critically-damped spring (`FOLLOW_SETTLE_MS` 240 ms) + 280 ms flip, curve recompute 42 ms throttle, scrollbar 0.25 s fade + 1.2 s idle, theme transition 0.35 s, staggered card fade-in on view/device switch (the same √ factor `t` drives both the delay and each card's own duration: near cards land slower (`STAGGER_FADE_NEAR_MS` 260 ms) and far cards faster (`STAGGER_FADE_FAR_MS` 150 ms), so the tail closes fast and dense; each card drops in from 6 px above (`STAGGER_DROP_PX`) and lands with a light overshoot that settles crisply — `EASE_OUT_BACK` = cubic-bezier(0.2, 1.5, 0.3, 1) (overshoot ≈ 5%; the amount is set by `P1.y`: 1.5 ≈ 5%, 1.8 ≈ 12%), deliberately the same tail shape family as `EASE_OUT_SOFT` so the recovery is not mushy: "splay downward, then a light bounce"; all delays are computed up front and follow a **diagonal** weight (`row + column`) — one anti-diagonal starts together and the wave sweeps top-left → bottom-right — as `window × √(weight / max weight)`, so the **gaps shrink towards the end** (front sparse, tail dense); the window is `min(200 ms, max weight × 14 ms)` (`STAGGER_WINDOW_MS` / `STAGGER_STEP_MS`); played via WAAPI with `fill: backwards` so late cards stay hidden while they wait — `lib/staggerIn.ts`). The frequency-response curve morphs on its own: any change to the path is tweened smoothly (a `useLayoutEffect` in `CurvePlot`) regardless of cause — channel switch, filter toggle, parameter drag, device switch all take the same route, so callers never special-case "should this animate". The tween starts from the previous animation's **current position** (`commitStyles()`, falling back to the previous target) — reading `getComputedStyle(el).d` does not work, because React has already written the new `d` by layout time, so the tween degenerates into new → new and nothing is visible. A mid-morph target change therefore continues from where the curve is instead of snapping back; the tween stays entirely in pixel space — no dB↔range conversion and no clamping — because the curve and the axis are independent: the Y range (peak-adaptive, stepping every 2 dB) changes instantly along with the redrawn grid, while the curve simply travels from its old on-screen shape to its new one; both endpoints already sit inside the plot area, so the interpolated points do too (an earlier attempt converted by range and clamped, which squashed part of the curve flat against the top edge for a moment — reverted); continuous input (slider drags) therefore reads as exponential smoothing that settles on the exact value. Only one `d` animation runs at a time, and only the ones we start are cancelled (`curve.css`'s stroke transition is left alone). Sample counts are not fixed — `buildEvalFreqs` appends band centres, high-Q refinement points and neighbouring midpoints — while `d` interpolation requires matching command sequences, so `lib/pathMorph.ts` aligns both sides to the **union** of their key x positions rather than a uniform resample — uniform resampling dilutes the dozens of refinement points packed around a high-Q peak and flattens it, which reads as "a coarse curve turning into a fine one"; on the common grid the x positions correspond one-to-one, so only y interpolates and each key point rises or falls in place instead of the whole line being kneaded; mismatched x spans (resize) return `null` and no animation runs. Duration matches the stroke transition at 320 ms / cubic-bezier(0.4, 0, 0.2, 1), with no `fill`, so resampling never pollutes the final rendered shape.
- Subpixel snapping via `snapPx()` for all positioning and animation endpoints.
