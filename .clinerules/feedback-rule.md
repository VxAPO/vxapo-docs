# Feedback 维护规则（v8.0，强制）

## 规则

**执行端实现中发现的规范问题反馈，统一记录于根目录 `feedback.md`，禁止写入 `roadmap.md`。**
`roadmap.md` 只保留条目状态、DoD 与规范落点；反馈与修订历史外置——保持路线清单精简。

## 触发条件

以下任一动作发生，即触发本规则：

- 执行端实现中**发现规范不可行/遗漏/矛盾/缺陷**（同 `主规范 十七` 反馈闭环）
- 实现完成报告随附的**潜在问题**（执行端自查发现，尚未定性为规范缺陷）
- 用户/规范侧对已落地规范提出**修订意见**（产品决策、澄清、严格化）

> **边界**：属产品意图（intent.md）的意愿变更不落 feedback.md——走 `.clinerules/intent-rule.md` 解耦治理。

## 记录格式（严格遵循）

`feedback.md` 为**逆序插入**（最新反馈在最上），每条包含：

```markdown
### [PX-X] <一句话问题标题>（版本号 <vX.Y> + 来源 <执行端反馈/用户决策/规范侧>）

**影响版本**：规范 vX.Y（首次涉及的定稿版本；若属后期修订则标 vX.Y 起）

**问题**：
- 具体描述（触发场景 / 现象 / 根因）

**规范侧判定**：
- 已确认缺陷（对应章节）/ 需用户决策 / 维持现状 + 理由

**修订记录**（规范侧处理，可多轮）：
- vX.Y：<修订动作摘要>——**对应章节**：`文件 节号`
- vX.Y+1：……（后续补充修订同此格式）

**状态**：已修订（vX.Y） / 待修订 / 维持现状
```

## 生命周期

```
执行端实现 → 发现规范问题 → feedback.md 新增记录（影响版本 + 问题 + 规范侧判定）
  → 规范侧核对 → 修订规范（版本递增 + changelog）→ 记录追加「修订记录」
  → 执行端继续实现 → 若再次发现问题 → 新增/追加同条记录
  → 修订全部落地 → 状态标记「已修订」
```

## 与现有机制的衔接

| 机制 | 关系 |
|------|------|
| `roadmap.md + roadmap-rule` | roadmap 条目命中的反馈**只留引用**：`> 反馈记录：feedback.md #PX-X`；状态机/DoD 不受反馈外置影响 |
| `主规范 十七（实现反馈闭环）` | v8.0 起反馈落点由 roadmap → feedback.md；其余闭环语义不变（执行端不改状态 + 零容忍绕过 + 规范侧修订） |
| `changelog-rule` | 反馈驱动的规范修订仍**必须走 changelog**（版本递增 + 记录）——feedback-rule 不替代 changelog-rule |
| `spec-finalize` skill | 定稿审查若涉及反馈，核对 feedback.md 对应记录的状态 |

## 自检清单

- [ ] 新反馈已写入 `feedback.md`（含 PX-X + 版本号 + 问题 + 规范侧判定）？
- [ ] `roadmap.md` 未新增反馈正文（仅引用）？
- [ ] 反馈驱动的规范修订已同步 changelog + 版本号？
- [ ] 修订完成后 feedback.md 状态已更新？
- [ ] 反馈中引用的章节号与修订后规范保持一致？

## 反例（禁止）

- 反馈正文写入 `roadmap.md`（导致清单臃肿）
- feedback.md 记录无版本号 / 无 PX-X（无法追溯归属）
- 反馈驱动的修订未更新 changelog（违反 changelog-rule）
- 修订后不更新 feedback.md 状态（历史失真）
