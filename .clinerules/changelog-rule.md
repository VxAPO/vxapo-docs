# Changelog 维护规则（强制）

## 规则

**每次版本更新后，必须维护项目根目录的 `changelog.md`，如实记录该版本的改动。**

## 触发条件

以下任一动作发生，即触发本规则：

- 主规范 `模块引用规范（无详细模块版）.md` 首行版本号递增（`vX.Y` → `vX.Y+1`）
- 任意详细模块规范新增/删除了"关键设计决策"级变更（含本文件之外的 `*模块规范.md`）
- 任何 git commit message 标有 `bump` / `feat` / `fix` 且影响规范语义

## 执行步骤

1. **先改版本号**：更新 `模块引用规范（无详细模块版）.md` 首行 `# 模块引用规范文档 vX.Y`
2. **再维护 changelog.md**：在文件**顶部逆序插入**一条新记录（最新版本在最上）
3. **记录格式**（严格遵循）：

```markdown
## vX.Y — YYYY-MM-DD

变更类型：`结构重构` / `缺陷修复` / `实现对齐` / `外部借鉴` / `文档同步`

- **条目 1**：一句话描述（参照该版本的"关键设计决策摘要补记"表）——**对应章节**：`模块 节号`（如 `pipeline 4.5/4.6`、`object 7.1.11`）
- **条目 2**：……——**对应章节**：`模块 节号`
- **条目 N**：……——**对应章节**：`模块 节号`
```

> **commit 记录（一次性，v8.3 废止回填循环）**：每条记录在**该版本提交完成时**填写
> `对应 commit：短hash`（若在 git 管理下）——**此后禁止回填/追加提交**。
> 后续版本更新只新增顶部记录，**不得修改已发布版本的 commit 行**。
> **章节号要求**：每条变更新增内容必须标注**关键章节号**（精确到 `文件名 + 节号`），
> 便于定位改动位置。若同一条涉及多节，用 `/` 分隔（如 `object 7.1.3/7.1.11`）。
> 参照该版本的"关键设计决策摘要补记"表的**落点列**。


4. **提交前自检**：`git diff` 中应同时包含版本号变更与 `changelog.md` 新增记录——若 changelog.md 未更新，禁止提交。
5. **commit 回填（v8.3，一次完成）**：版本提交后一次性回填该记录的 `对应 commit：短hash`；
   **不允许**为了回填 hash 而再次追加提交（回填仅本地补写，随下次自然变更一并提交）——
   更不允许「回填 → 出新版本 → 又改旧版记录」的**回填循环**。已发布版本记录**冻结**，一律不改。

## 范围约定

- **历史回溯**：`changelog.md` 从 **v6.6** 开始记录，v6.6 之前版本（v6.0-v6.5）无需补录
- **未来强制**：此后每一个新版本（v6.10+ / v7+ 等）发布时，都必须满足本规则
- changelog.md 与主规范版本号必须**一一对应**——不允许"版本号已递增但 changelog 缺该版本"

## 反例（禁止）

- 只改版本号、不更新 changelog.md
- changelog.md 记录了未实际发生的改动
- 记录顺序颠倒（旧版在上）
- 变更描述与"关键设计决策摘要补记"表不一致
- **回填循环**：已发布版本记录再次追加 commit（回填 → 出新版本 → 又改旧版 → 再提交）
- **为回填 hash 单独提交**（回填属本地补写，随下次自然变更一并提交）
- 修改已发布版本的 commit 行（已发布记录冻结）
